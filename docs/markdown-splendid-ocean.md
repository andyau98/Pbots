管工到貨收貨後影相或轉 PDF，貨單格式多變。如何有效提取資料係成個系統嘅第一關。

### 1.5.4 Plan B：OCR 讀錯嘅處理策略

Plan B 要處理 OCR 出錯嘅實際情況。幕牆工地貨單上常見嘅 OCR 問題：

#### 常見 OCR 錯誤類型

| 錯誤類型 | 例子 | 出現原因 |
|----------|------|----------|
| 字元混淆 | `0`↔`O`, `1`↔`l`↔`I`, `5`↔`S`, `8`↔`B` | 字體/影相角度 |
| 中英混雜 | `鋁板` → `铝板` / `鋁饭` | 繁體簡體混淆、相似字 |
| 分隔符丟失 | `ACA-FST-101` → `ACAFST101` / `ACA FST 101` | OCR 忽略標點 |
| 表格線干擾 | 表格線被當成文字 `|` `l` `1` | 影相質素低 |
| 手寫體文字 | 人手填寫嘅數字/文字無法識別 | 手寫辨識率低 |
| 部分遮擋 | 貨單摺痕/釘書釘遮住部分文字 | 物理損壞 |
| 影相角度變形 | 斜角影相導致文字變形 | 現場快速影相 |

#### 應對策略 B1：落單號驗證 + 自動修正

落單號有固定格式規則，可以用嚟驗證 OCR 結果：

```js
function validateOrderNumber(raw) {
    // 清理：移除空格、統一大小寫
    let cleaned = raw.replace(/\s+/g, '').toUpperCase();

    // 修正常見 OCR 錯誤
    cleaned = cleaned
        .replace(/0(?=[A-Z])/g, 'O')    // 0→O（如果後面跟字母）
        .replace(/(?<=[A-Z])0/g, 'O')    // 字母後的 0→O
        .replace(/1(?=[A-Z]{2})/g, 'I')  // 特定場景 1→I
        .replace(/5(?=[A-Z])/g, 'S')     // 5→S（如果後面跟字母）
        .replace(/8(?=[A-Z])/g, 'B');    // 8→B（如果後面跟字母）

    // 驗證格式：至少要有 project code + material code
    // 例如 ACA-FST-101 或 HGRH-BTB0102-FST4152B
    const validPattern = /^[A-Z]{2,4}[-_]?[A-Z0-9]+[-_]?[A-Z]?\d{2,6}/;

    if (validPattern.test(cleaned)) {
        return { valid: true, cleaned, confidence: 'high' };
    }

    // 寬鬆匹配：至少要有字母+數字組合
    const loosePattern = /[A-Z]{2,}.*\d{2,}/;
    if (loosePattern.test(cleaned)) {
        return { valid: true, cleaned, confidence: 'low' };
    }

    return { valid: false, cleaned, confidence: 'none' };
}
```

#### 應對策略 B2：已知物料碼比對

用現有 `MATERIAL_CODES`（FST/FAC/BGL/ACD...）驗證提取結果：

```js
const KNOWN_MATERIALS = ['FST','FAC','BGL','ACD','BOM','FHA','FSS','HGRH','MSA','MSB','MSH','JMA','AP','BBF','BGK','FFA','FHU','UN'];

function validateMaterialCode(text) {
    // 喺 OCR 文字中搜尋已知物料碼
    const found = [];
    for (const code of KNOWN_MATERIALS) {
        if (text.toUpperCase().includes(code)) {
            found.push(code);
        }
    }
    // 按出現順序排序 → 第一個可能係主物料碼
    return found;
}
```

#### 應對策略 B3：供應商名模糊匹配

```js
function matchSupplier(ocrText) {
    const suppliers = dataStore.get('suppliers', []);
    for (const s of suppliers) {
        // 供應商名嘅任何一個關鍵字出現喺 OCR 文字就當匹配
        const keywords = s.name.split(/[\s\-\(\)（）]+/);
        const matchCount = keywords.filter(k => ocrText.includes(k)).length;
        if (matchCount >= 2) return { supplier: s.name, confidence: 'high' };
        if (matchCount === 1) return { supplier: s.name, confidence: 'low' };
    }
    return { supplier: null, confidence: 'none' };
}
```

#### 應對策略 B4：多重 confidence level 處理

| Confidence | 動作 |
|------------|------|
| **High** (≥80%) | 自動填入，用戶只睇摘要確認 ✅ |
| **Medium** (50-79%) | 顯示提取結果 + ⚠️ 標記不確定欄位，用戶需確認 |
| **Low** (<50%) | 直接跳去人手輸入模式，唔顯示不可靠結果 |
| **None** | 直接人手輸入 |

#### 應對策略 B5：圖像預處理改善 OCR

```js
// 用 sharp 預處理相片，提升 OCR 準確率
async function preprocessImage(inputPath, outputPath) {
    await sharp(inputPath)
        .grayscale()           // 轉灰階
        .normalize()           // 增強對比度
        .sharpen()             // 銳化
        .threshold(128)        // 二值化（黑白分明）
        .resize(2000, 2000, { fit: 'inside' })  // 限制最大尺寸
        .toFile(outputPath);
}
```

#### 應對策略 B6：當 OCR 完全失敗時

如果 OCR 完全無法提取任何有用資料（例如手寫單、極模糊相片）：

1. 提示用戶：「❌ 無法自動讀取貨單內容，請選擇：」
2. 選項 A：重影貨單（改善光線/角度）

4. 選項 C：留低相片記錄，稍後人手補入（標記為 pending）

#### Levenshtein 模糊匹配（純 JS，無需 npm）

```js
function levenshtein(a, b) {
    const m = a.length, n = b.length;
    const dp = Array.from({ length: m + 1 }, () => Array(n + 1).fill(0));
    for (let i = 0; i <= m; i++) dp[i][0] = i;
    for (let j = 0; j <= n; j++) dp[0][j] = j;
    for (let i = 1; i <= m; i++)
        for (let j = 1; j <= n; j++)
            dp[i][j] = a[i - 1] === b[j - 1]
                ? dp[i - 1][j - 1]
                : 1 + Math.min(dp[i - 1][j], dp[i][j - 1], dp[i - 1][j - 1]);
    return dp[m][n];
}

### 1.6 反向驗證策略（Plan C）— Folder 先行，已知數據引導 OCR

用戶提出嘅核心洞察：

> 先讀取貨單對應嘅 folder → folder 上有數量表 + TG drawing → 已知貨品編號同數量 → 反向指定讀取 → 判決 OCR 錯誤

呢個係一個**根本性嘅策略轉變**。傳統 OCR 係「讀咗先算，之後驗證」；反向策略係「先鎖定目標，再用目標清單去校對 OCR」。

#### 1.6.1 概念對比

```
傳統 Plan A/B（盲讀 → 驗證）:
  貨單 OCR → 提取所有文字 → 嘗試匹配 → 唔知啱唔啱

反向 Plan C（目標 → 驗證 → 修正）:
  貨單 OCR → 只提取 1-2 個最可靠欄位 → 定位 POR folder
    → 讀取 folder 內嘅數量表 → 獲得「應該有嘅物料清單」
    → 用清單反向驗證 OCR 結果 → 修正錯誤 → 高準確度輸出
```

#### 1.6.3 誤讀降低分析

| 傳統 OCR（盲讀） | 反向驗證（Folder 先行） | 改善 |
|------------------|------------------------|------|
| 讀取所有文字 → 大量 noise | 只搵已知圖號 → 精準 | ⬆️ 90% |
| `ACDOO6O` → 無法識別 | `ACDOO6O` → Levenshtein 匹配 `ACD0060` | ✅ 修正 |
| 數量 `3O` → 讀成文字 | `3O` → 已知預期係 `30` → 自動修正 | ✅ 修正 |
| 手寫數字 5/S 混淆 | 已知預期 50 → 排除 S0 | ✅ 修正 |
| 漏讀某行 → 無發現 | 已知清單有 → 標記缺失 | ✅ 偵測 |
| 多讀 noise → 假陽性 | 已知清單冇 → 標記新增 | ✅ 隔離 |

#### 1.6.4 關鍵前提

| 前提 | 依賴 | 狀態 |
|------|------|------|
| 能從貨單提取到足夠定位 folder 嘅資訊 | 項目碼+物料碼（4-6字母） | ✅ 極高成功率 |
| POR folder 內有數量表 Excel | 用戶提供 | 🔴 需確認有冇 |
| 數量表格式可被讀取 | exceljs | 🟡 需範例 |
| files 表已建立 POR 索引 | `#searchpor` 命令 | ✅ 現有功能 |
| tg_mapping 已建立 | `#rebuildTg` 命令 | ✅ 現有功能 |

#### 1.6.5 如果數量表唔存在嘅 fallback

如果某個 POR folder 冇數量表 Excel，可以用 TG 位置圖做替代：

```
冇數量表 → 查 tg_mapping 表
  → 該 folder 嘅 TG 位置圖上有乜嘢繪圖編號
  → 用繪圖編號清單代替數量表清單
  → 至少知道「應該有邊啲加工圖號」
  → 數量就無法驗證（要人手輸入）
```

#### 1.6.6 混合策略：Plan A + B + C 分層

最穩健嘅做法係三者互補：

```
第一層（Plan C）：Folder 先行 → 用已知清單定向 OCR → 高準確度
  ↓ 失敗？
第二層（Plan A）：傳統 OCR + 正則匹配 → 中準確度
  ↓ 仍然失敗？
第三層（Plan B）：OCR 修正規則 + confidence 分級 → 低準確度但可用
  ↓ 完全失敗？
第四層：人手輸入模式
```

每層失敗先跌落下一層，最大程度減少人手輸入。

### 1.8 自適應數量表讀取 — 解決格式不一嘅問題

#### 1.8.1 問題

每個 POR folder 嘅數量表 Excel 格式都唔同：
- 欄位次序唔同（圖號可能喺 Column A、B、C...）
- 標題行位置唔同（有啲有 header、有啲冇）
- 中英混合標題（「圖號」「Drawing No」「Qty」「數量」）
- 有啲有合併儲存格、有空行

**用戶確認嘅關鍵事實：**
- 數量表一定喺 folder 上
- Folder 名就係單號
- 加工圖號同時出現喺數量表 Excel 同 TG 位置圖上

#### 1.8.2 核心策略：已知圖號做錨點

唔需要知 Excel 格式 → 用**已知嘅加工圖號**反向定位數據位置。

```
我哋已經知道（來自 files 表 + tg_mapping）：
  POR folder "POR1469 HGRH-ACA-FST..."
    內含加工圖號：ACD0060, ACD0061, ACD0062, ACD0063, ...

策略：
  喺 Excel 入面搜尋呢啲已知圖號 → 搵到佢哋嘅位置 → 反推欄位結構
```

#### 1.8.3 五步自適應讀取流程

```
Step 1: 搵到數量表檔案
─────────────────────────────────────────────
掃描 POR folder 內所有 .xlsx 檔案
  → 排除暫存檔（~$開頭）
  → 優先揀檔名含「數量」「BOM」「Qty」「物料」嘅
  → 如果多個候選 → 每個都試讀 → 揀最多已知圖號命中嗰個


Step 2: 提取已知圖號清單（三來源交叉驗證）
─────────────────────────────────────────────
來源 A — files 表:
  SELECT DISTINCT name FROM files
  WHERE folder = '<por_folder_path>'
    AND ext IN ('.dwg', '.pdf')
    AND has_tag = 0

來源 B — folder_cache 表:
  SELECT drawing_numbers, drawing_files FROM folder_cache
  WHERE folder = '<por_folder_path>'

來源 C — tg_mapping 表:
  SELECT DISTINCT drawing_number FROM tg_mapping
  WHERE file_path IN (
    SELECT path FROM files
    WHERE folder = '<por_folder_path>' AND has_tag = 1

合併 → 去重 → 標準化（大寫、移除分隔符）
  → 已知圖號清單: ['ACD0060', 'ACD0061', 'ACD0062', ...]


Step 3: 掃描 Excel → 定位錨點
─────────────────────────────────────────────

  → 逐 cell 掃描
  → 每個 cell 值同已知圖號清單做 Levenshtein 模糊比對
  → 匹配到 → 記錄 { row, col, drawingNumber, cellValue }

結果例如:
  匹配 1: ACD0060 → Row 5, Col B
  匹配 2: ACD0061 → Row 6, Col B
  匹配 3: ACD0062 → Row 7, Col B
  匹配 4: ACD0063 → Row 8, Col B

從呢啲錨點推斷：
  → Column B 係「圖號」欄（所有匹配都喺同一 column ✅）


Step 4: 推斷其他欄位
─────────────────────────────────────────────
對於每個匹配到嘅 row，分析同一 row 嘅其他 columns：

  Row 5: [A:1] [B:ACD0060] [C:鋁板 2mm] [D:50] [E:件]
          │       │              │           │      │
          ▼       ▼              ▼           ▼      ▼
       整數=1  已知錨點      含中文文字   純數字   短文字=

Column A: 全部都係正整數 → 序號
Column B: 已知錨點 → 圖號 ✅
Column C: 含中文/英文文字 → 描述
Column D: 全部都係數字 → 數量
Column E: 「件」「套」「m²」等 → 單位

推斷規則（按優先級）：
┌──────────────┬────────────────────────────────────┐
│ 數據特徵      │ 推斷欄位                            │
├──────────────┼────────────────────────────────────┤
│ 匹配已知圖號  │ → 圖號 (drawing_number)            │
│ 純正整數 1-99 │ → 序號 (sequence)                  │
│ 純數字（含小數)│ → 數量 (quantity)                  │
│ 單位關鍵字    │ → 單位 (unit)                      │
│    件/set/pcs/m²/kg/噸/支/套/組/個                │
│ 含中文長文字  │ → 描述 (description)               │
│ 含英文長文字  │ → 規格 (specification)             │
│ 日期格式      │ → 日期 (date)                      │
│ 其他          │ → 備註 (notes)                     │
└──────────────┴────────────────────────────────────┘


Step 5: 驗證 + 輸出
─────────────────────────────────────────────
檢查：
  ✅ 至少有一 column 匹配到 ≥2 個已知圖號（確認圖號欄存在）
  ✅ 數量 column 嘅值全部都係合理數字（>0, <100000）
  ✅ 圖號數量 ≈ 數量欄數量（每 row 都有對應）

如果驗證通過 → 輸出結構化數據：

    { seq: 1, drawing: 'ACD0060', desc: '鋁板 2mm', qty: 50, unit: '件' },

#### 1.8.4 輔助策略：標題行檢測

即使格式不一，大部分 Excel 都有標題行。用關鍵字檢測：

```js
const HEADER_KEYWORDS = {
    drawing: ['圖號', '編號', 'Drawing', 'DW No', 'DWG No', 'Item', 'Code', '號碼', '編碼'],
    quantity: ['數量', 'Qty', 'Quantity', '件數', 'Pcs', '數量', '總數'],
    description: ['描述', 'Description', '物料', 'Material', '名稱', 'Name', '內容', '項目'],
    specification: ['規格', 'Spec', 'Size', '尺寸', '型號', 'Model'],
    unit: ['單位', 'Unit', '備註'],
    sequence: ['序號', 'No.', '#', '項次', 'Item'],
};

function detectHeaderRow(worksheet, maxScanRows = 10) {
    for (let row = 1; row <= maxScanRows; row++) {
        const cells = worksheet.getRow(row);
        let keywordHits = 0;
        const colMap = {};  // col → 推斷欄位類型

        cells.eachCell((cell, col) => {
            const val = String(cell.value || '').trim();
            for (const [field, keywords] of Object.entries(HEADER_KEYWORDS)) {
                if (keywords.some(kw => val.includes(kw))) {
                    colMap[col] = field;
                    keywordHits++;
                }
            }
        });

        if (keywordHits >= 2) {
            return { headerRow: row, colMap, confidence: keywordHits };
        }
    }
    return null;  // 冇標題行 → 全靠錨點推斷
}
```

```sql

FROM tg_mapping
WHERE file_path IN (
    SELECT path FROM files

)
```

呢個可以用嚟：

- **驗證**數量表提取結果（數量表有嘅圖號，TG 上都應該有）
- **偵測**數量表缺失項（TG 有但數量表冇）

#### 1.8.7 無人手介入 — 純編程 vs AI 分析

##### 用戶要求

唔要人手介入。能否用免費 AI 讀取分析？還是可以用編程做？

##### 答案：純編程已足夠，唔需要 AI

原因：我哋嘅場景**唔係通用 OCR**，而係**已知目標嘅定向搜尋**。AI 對「理解任意 Excel 格式」有優勢，但我哋已經知道每個 folder 內有咩加工圖號 — 呢個係決定性優勢。

##### 編程 vs AI 對比

| | 純編程（錨點策略） | AI（LLM 分析） |
|---|---|---|
| **做法** | 用已知圖號掃描 Excel → 定位 → 推斷欄位 | 上傳 Excel 俾 AI → AI 描述結構 |
| **速度** | <100ms（本地 SQL + exceljs） | 1-5 秒（API 延遲） |
| **成本** | $0 | 每次 API call 收費 |
| **準確度** | 極高（已知圖號 = 絕對參考點） | 中等（AI 可能誤解格式） |
| **離線可用** | ✅ | ❌（需要網路） |
| **隱私** | ✅ 數據唔離開伺服器 | ❌ Excel 內容上傳到第三方 |
| **依賴** | 無新依賴 | 需 API key + 網路 |

**結論：呢個場景下，純編程比 AI 更快、更準、更可靠、更私隱。**

##### 點解純編程就夠？

關鍵在於我哋**有已知圖號清單**，呢個係 AI 冇嘅絕對參考點：

```
AI 睇 Excel: 「呢個 column 係咩？似係圖號...可能係...」
    ↓ 推測，可能出錯

程式睇 Excel: 「Column B 有 ACD0060, ACD0061, ACD0062...
    呢啲全部都喺我嘅已知清單入面 → Column B 100% 係圖號欄」
    ↓ 絕對肯定，唔會錯
```

##### 如果真係要 AI 做後備

唯一需要 AI 嘅情況：錨點完全搵唔到（數量表冇任何已知圖號）。

呢個情況極罕見 — 因為：

|---------|------|------|

**建議：唔需要。純編程錨點策略已覆蓋 >95% 情況。**

##### 加強錨點策略 — 做到零人手介入

要確保錨點策略萬無一失，加以下增強：

```
增強 1: 多級模糊匹配
─────────────────────
嘗試 1: 精確匹配（大寫、去分隔符）
  → 命中率通常 >90%

嘗試 2: Levenshtein 距離 ≤ 2
  → 命中率 +8%（修正 OCR/手誤）

嘗試 3: 子字串匹配（Excel cell 包含已知圖號）
  → 例如 cell 值 = "鋁板 ACD0060 2mm" → 包含 ACD0060 ✅

嘗試 4: 部分匹配（已知圖號的數字部分）
  → 例如 0060 出現喺 cell → 可能係 ACD0060

增強 2: 多 Column 驗證
─────────────────────
如果多於一個 column 有候選圖號：
  → 揀命中數量最多嗰個
  → 揀 cell 值最短嗰個（圖號通常短，唔會係描述欄）

增強 3: 數量欄雙重確認
─────────────────────
候選數量 column 必須：
  ✅ 所有值都係數字或純數字字串
  ✅ 至少 70% 嘅值 > 0
  ✅ 冇超過 100,000（異常大數量）
  
增強 4: 一致性評分
─────────────────────
每個候選格式方案計分：
  +10分: 圖號欄命中 ≥5 個已知圖號
  +10分: 圖號命中全部喺同一 column
  +5分:  數量欄全部係數字
  +5分:  檢測到標題行有已知關鍵字
  +3分:  數量 row 數 = 圖號 row 數
  -5分:  多個 column 有相同數據模式（混淆）
  
  最高分方案 → 自動採用（唔問用戶）
  如果最高分 ≥ 20 → 信心足夠，直接輸出 ✅
```

##### 最終方案

```
自適應讀取 → 一致性評分
  │
  ├─ 評分 ≥ 20 → 自動採用（預計 >95% 情況）
  │
  ├─ 評分 10-19 → 自動採用 + 日誌記錄（方便日後除錯）
  │
  └─ 評分 < 10 → 自動採用 + WhatsApp 顯示「⚠️ 格式不確定，請核對」
                 （只係提示，唔會阻塞流程）
```

**零人手介入，全靠編程自適應。**
